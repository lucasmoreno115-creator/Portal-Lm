# F4.0 — Premium Gap Audit

> Audit date: 2026-08-14  
> Source of truth: repository runtime, HTTP handlers, presenters and tests on the post-F3.4.4/F2.1.1 baseline.  
> Change policy: this audit changes no production runtime, schema, migration, endpoint or UI.

## Executive Summary

The Premium product has two proven operational backbones: the consultation lifecycle and the Weekly Feedback full-response flow. Student creation/access, anamnesis review, the professional Workspace/Student Record core, deactivation/reactivation, and nutrition plan version storage also have meaningful automated evidence.

The product is **not yet operationally complete**. The principal remaining break is not lifecycle or Weekly Feedback: it is parity in the surrounding product. The nutrition editor persists more information than the Home-linked student page exposes; progression loses fields at its write boundary and has no professional reading/feedback surface; the professional weekly-plan flow has current-week editing but no explicit publication/history operation; and training is an external MFIT link rather than an observable Portal cycle.

This audit found **10 gaps**: **0 P0, 5 P1, 3 P2 and 2 P3**; severities are **0 S0, 5 S1, 3 S2 and 2 S3**. No previously validated contract was found regressed. Surfaces counted by their aggregate status: **8 VALIDATED, 6 FUNCTIONAL_WITH_GAP, 4 PARTIAL, 1 NOT_CONNECTED, 0 REGRESSION and 1 NOT_APPLICABLE**. Browser-only visual behavior is explicitly marked `REQUIRES_STAGING_VALIDATION`, not inferred.

## Audit Scope

Personas: professional/admin, Premium student, and a dual-product student. The audit covers registration/access, onboarding and anamnesis, Workspace, Student Record, consultation lifecycle, nutrition planning/versioning, weekly objectives, training, progression, Weekly Feedback and delivered feedback, Home, library, help, navigation, access boundaries, error/double-submit behavior, sensitive data, observability, runtime duplication and test evidence.

Projeto LM was considered only at the shared-identity/product boundary. Its lifecycle, progress, plans and pending work are outside the feature scope and must remain independent.

## Method

1. Traced each journey from HTML/JS consumer to HTTP handler, application/repository code and presenter.
2. Compared professional source → persisted fields → public DTO → student renderer.
3. Inventoried CRUD verbs and explicit publication/version semantics rather than treating a page or HTTP 200 as completion.
4. Searched runnable Premium surfaces for placeholders, mock actions, dead links, disabled actions, alerts and console-only behavior, then inspected context.
5. Mapped relevant automated suites and retained the supplied real-staging `FULL_RESPONSE_FLOW = VALIDATED` evidence without issuing new staging mutations.
6. Applied `VALIDATED` only where implementation, boundary integration and relevant tests coexist. Structural browser findings remain `REQUIRES_STAGING_VALIDATION`.

Classification is an aggregate product assessment; a PASS at one parity stage does not make the whole surface validated.

## Current Architecture

- `workers/api.js` is the active HTTP composition root. Premium application, repository, domain and presenter modules live under `workers/premium/`.
- Professional operations use `admin-premium-workspace.html`, `admin-premium-student-record.html`, nutrition/objectives editors and `/api/admin/premium/*` contracts. A legacy `/api/admin/weekly-plan` email-based editor still exists.
- Student Premium entry is `portal-premium-home.html`. It calls server-gated Premium resources and links to a mix of canonical Premium pages, legacy-compatible pages and MFIT/WhatsApp.
- Premium identity is shared at login, while `getPremiumGate` and `blockProjectLmOnPremiumCore` enforce the operational product boundary server-side.
- Nutrition has a versioned canonical repository but two public DTO/page pairs: Home navigates to the older `/api/portal/nutrition-plan` renderer while `/api/portal/premium/nutrition-plan/current` and `portal-premium-nutrition-plan.html` form a newer, currently navigation-orphaned pair.
- Root, `public/`, and `public/assets/js/` runtime copies are intentionally guarded for byte identity. This is deployment debt, not a reason to consolidate in F4.0.

## Validated Capabilities

- Canonical lifecycle through activation, deactivation and reactivation, including Premium/Projeto LM isolation.
- Weekly Feedback current submission → pending → professional review/response → resolved → reload/idempotent correlation.
- Current Weekly Feedback UI does **not** collect `waist` or `abdomen`. Compatibility fields remain in repositories/presenters for historical rows only; a new current-UI payload is generated exclusively from `ANSWER_FIELDS`, whose collection contract excludes them. **NOT A GAP**.
- Professional Workspace summary/queues/student cards and canonical navigation to Student Record.
- Student creation, canonical `student_id`, duplicate protection and one-time access delivery/recovery contracts.
- Student and professional anamnesis submission/review, `analyzed_at`, pending resolution and lifecycle transition.
- Nutrition draft → publish V1 → duplicate to draft → publish V2 while preserving V1 in history at repository/API level.
- Premium access denial after ENDED and restoration after reactivation at protected HTTP resources.

## Gaps

### GAP-PREM-001 — Progression write contract discards student results

- **Surface / classification:** Progression / NOT_CONNECTED
- **Severity / priority / layer:** S1 HIGH / P1 / student UI ↔ HTTP persistence
- **Evidence:** `portal-progressao.html` sends `recommendation` and `executionQuality`; `/api/portal/progression` reads `decision` and `rir`, then persists defaults when those absent. The GET renderer consequently falls back to stored `decision`, not the calculated recommendation. Existing Premium tests only assert access/isolation and route presence.
- **Expected:** exercise, target range, load, reps, execution quality and the calculated recommendation round-trip unchanged.
- **Observed:** exercise/range/load/reps persist; quality is not stored and recommendation becomes the backend default “Manter carga”.
- **Impact:** the visible history can contradict the decision shown before save, destroying trust in the core progression record.
- **Files:** `public/portal-progressao.html`; `workers/api.js`; `database/expected/migration-schema.sql`; `tests/lm-premium-legacy-contracts.test.mjs`.
- **Tests existing:** access contract only; no field parity test.
- **Recommendation:** define one canonical progression DTO and contract-test POST→GET field equality before touching UI.
- **Proposed phase:** F4.1 — Progression Contract and Professional Loop.

### GAP-PREM-002 — Progression has no professional reading or feedback loop

- **Surface / classification:** Progression + Student Record / PARTIAL
- **Severity / priority / layer:** S1 HIGH / P1 / professional read model and UX
- **Evidence:** student POST/GET routes exist, but the Student Record presenter returns student, summary, anamnesis, nutrition, feedbacks, follow-ups and pending only. No Premium admin progression endpoint/consumer or exercise/training link exists.
- **Expected:** professional can inspect a student's progression history, associate it with training/exercise and provide or record guidance.
- **Observed:** the student can save/read personal logs only; the professional cannot observe the cycle.
- **Impact:** progression cannot support consultative decisions and the Student Record is not 360º.
- **Files:** `workers/premium/presenters/student-record-presenter.js`; `workers/api.js`; `public/admin-premium-student-record.js`; `public/portal-progressao.html`.
- **Tests existing:** no professional progression suite.
- **Recommendation:** after fixing GAP-001, add a student-scoped professional read model, history UI and an explicit feedback/pending contract; do not couple to Projeto LM progression.
- **Proposed phase:** F4.1 — Progression Contract and Professional Loop.

### GAP-PREM-003 — Home-linked nutrition page is not at parity with published plans

- **Surface / classification:** Nutrition public parity / NOT_CONNECTED
- **Severity / priority / layer:** S1 HIGH / P1 / presenter, route and student renderer
- **Evidence:** Home links `portal-plano-alimentar.html` → `/api/portal/nutrition-plan` → `publicNutritionPlan`. That legacy projection omits canonical `observations`, hydration, supplements and publication metadata, while the renderer also omits title, goal, strategy and adherence rules. A newer canonical presenter/page exists and is tested but is not linked by Home/menu.
- **Expected:** everything professionally published that is part of the public contract is represented accurately to the student, with current-version identity.
- **Observed:** meals and substitutions render, but multiple published fields and current-version context disappear in the actual Home journey.
- **Impact:** the student can follow meals yet miss clinically/operationally relevant directions; professional cannot know that the student sees the complete published plan.
- **Files:** `public/portal-premium-home.html`; `public/portal-shared.js`; `public/portal-plano-alimentar.html`; `public/portal-premium-nutrition-plan.html`; `workers/api.js`; `workers/premium/presenters/nutrition-plan-public-presenter.js`.
- **Tests existing:** strong repository/versioning and isolated renderer tests; no canonical editor→Home-linked renderer parity E2E.
- **Recommendation:** choose a single public route/presenter/renderer, explicitly map every supported published field, show version/update context and add V1/V2 student-render assertions.
- **Proposed phase:** F4.2 — Published Nutrition Student Parity.

### GAP-PREM-004 — Weekly objectives lack an explicit publish/history lifecycle

- **Surface / classification:** Plano da Semana / PARTIAL
- **Severity / priority / layer:** S1 HIGH / P1 / domain, professional operation and history
- **Evidence:** the Premium objectives editor GETs/PUTs only the calculated current week and writes it directly `ACTIVE`; the public API selects the latest active row. There is no draft/publish transition, list/history UI or professional visibility into what prior weeks contained. The legacy email editor independently upserts the same table.
- **Expected:** professional can create/edit, deliberately publish/update the student's current week, identify what is live and consult preserved weekly history.
- **Observed:** a current-week save immediately becomes live; database rows can preserve different week refs, but the supported Premium UI cannot inspect or manage history.
- **Impact:** accidental partial edits become student-visible and weekly accountability lacks an operational audit trail.
- **Files:** `public/admin-premium-planning-objectives.js`; `public/admin-weekly-plan.html`; `workers/api.js`; `public/portal-premium-home.html`.
- **Tests existing:** current save→public read contract; no publication or history workflow test.
- **Recommendation:** define minimal current-week draft/publish/history semantics and retire the duplicate editor only in a future implementation block.
- **Proposed phase:** F4.3 — Weekly Objectives Publication and History.

### GAP-PREM-005 — Training is an unobservable external handoff

- **Surface / classification:** Training / PARTIAL
- **Severity / priority / layer:** S1 HIGH / P1 / integration and operational observability
- **Evidence:** Premium Home links directly to a generic MFIT URL. Portal stores/renders only a textual weekly training focus; there is no student-specific training availability, deep link, error/empty state, professional read status or Portal contract proving the correct MFIT assignment.
- **Expected:** a student reaches the correct assigned training and the professional can determine whether training is configured/available.
- **Observed:** the CTA opens MFIT; the actual assignment and identity linkage are outside observable Portal contracts.
- **Impact:** a central Premium promise can fail silently or open an unaffiliated external state.
- **Files:** `public/portal-premium-home.html`; `public/admin-premium-planning-objectives.js`; `workers/api.js`.
- **Tests existing:** structural Home tests only; integration is `REQUIRES_STAGING_VALIDATION`.
- **Recommendation:** first document/validate the MFIT ownership and deep-link contract; then expose a minimal availability/status read model rather than reimplementing training.
- **Proposed phase:** F4.4 — Training Handoff Reliability.

### GAP-PREM-006 — Library is static and has no content operations

- **Surface / classification:** Library / FUNCTIONAL_WITH_GAP
- **Severity / priority / layer:** S2 MEDIUM / P2 / content operations
- **Evidence:** eight educational entries are embedded in a client-side array; there is no origin metadata, admin consumer, content API, asset/link validation or empty/error state because no resource is loaded.
- **Expected:** content origin and ownership are explicit and maintainable; broken/missing content has observable behavior.
- **Observed:** accessible, useful static accordion content works, but every change requires deployment.
- **Impact:** low-frequency content maintenance and governance depend on code changes; this does not block the consultation core.
- **Files:** `public/portal-biblioteca.html`; `public/assets/js/lm-access.js`; `tests/nutrition-library.test.mjs`.
- **Tests existing:** structural content/navigation coverage.
- **Recommendation:** decide explicitly whether “static by design” is the product contract; only add administration if ownership cadence justifies it.
- **Proposed phase:** F4.6 — Student Experience Hardening.

### GAP-PREM-007 — Premium Home silently masks resource failures

- **Surface / classification:** Home + error handling / FUNCTIONAL_WITH_GAP
- **Severity / priority / layer:** S2 MEDIUM / P2 / student UX and observability
- **Evidence:** Weekly Feedback failure resets generic copy while leaving the link usable; weekly-plan failure only sets `data-state='error'` without inserting a visible error/retry message. Training/support availability cannot be checked.
- **Expected:** loading, empty and failed resource states are distinguishable and actionable without blocking unaffected resources.
- **Observed:** the page remains navigable, but some network/500 failures look like ordinary default content.
- **Impact:** students and support cannot distinguish “no update” from an outage; production failures can remain invisible.
- **Files:** `public/portal-premium-home.html`; `public/portal.css`.
- **Tests existing:** structural Home/loading tests, no browser network-failure scenario.
- **Recommendation:** add visible per-card error/retry states and browser-level failure tests in a later UI block.
- **Proposed phase:** F4.6 — Student Experience Hardening.

### GAP-PREM-008 — Home does not expose progression as an action

- **Surface / classification:** Home/navigation / FUNCTIONAL_WITH_GAP
- **Severity / priority / layer:** S2 MEDIUM / P2 / information architecture
- **Evidence:** plan-aware navigation includes `portal-progressao.html`, but neither primary nor secondary Home actions link progression despite the Home mission treating it as a Premium capability.
- **Expected:** Home directs the student to the next relevant Premium action, including progression when appropriate.
- **Observed:** progression is discoverable only through the menu.
- **Impact:** reduced discovery/frequency; it does not itself block an informed user.
- **Files:** `public/portal-premium-home.html`; `public/assets/js/lm-access.js`; `public/portal-progressao.html`.
- **Tests existing:** Home structure and access-menu tests; no journey assertion.
- **Recommendation:** solve GAP-001/002 first, then add contextual Home state/CTA rather than another unconditional card.
- **Proposed phase:** F4.6 — Student Experience Hardening.

### GAP-PREM-009 — Help delivery is outside Portal observability

- **Surface / classification:** Preciso de Ajuda / FUNCTIONAL_WITH_GAP
- **Severity / priority / layer:** S3 LOW / P3 / external-channel UX
- **Evidence:** Home/menu provide a valid WhatsApp deep link with prefilled message, but no fallback/contact copy, channel availability state or Portal acknowledgement exists.
- **Expected:** student can request help and understand what to do if the preferred channel cannot open.
- **Observed:** the CTA is real and actionable, but successful request delivery cannot be known by Portal.
- **Impact:** edge-case failure on devices without a usable WhatsApp handler; central support remains available for normal devices.
- **Files:** `public/portal-premium-home.html`; `public/portal-shared.js`; `public/portal-plano-alimentar.html`.
- **Tests existing:** structural link tests only.
- **Recommendation:** retain WhatsApp, expose visible contact/fallback copy and define that delivery acknowledgement belongs to WhatsApp, not Portal.
- **Proposed phase:** F4.6 — Student Experience Hardening.

### GAP-PREM-010 — Duplicate legacy/canonical runtimes obscure ownership

- **Surface / classification:** technical architecture / FUNCTIONAL_WITH_GAP
- **Severity / priority / layer:** S3 LOW / P3 / technical debt
- **Evidence:** root/public/assets copies are intentionally byte-identical; nutrition has old/new student pages and public projections; weekly objectives have legacy email-based and canonical student-id editors. Some new pages are test/PWA reachable but absent from product navigation.
- **Expected:** each operation has one documented product owner and one canonical consumer while required deployment copies stay mechanically generated.
- **Observed:** gates prevent drift in selected copies, but parallel consumers make it easy to test an orphan rather than the real journey.
- **Impact:** audit/test ambiguity and higher regression risk; current validated core remains usable.
- **Files:** `public/portal-plano-alimentar.html`; `public/portal-premium-nutrition-plan.html`; `public/admin-weekly-plan.html`; `public/admin-premium-planning-objectives.html`; root/public/assets runtime copies; `scripts/check-project-lm-runtime.mjs`.
- **Tests existing:** byte-identity and route inventory tests.
- **Recommendation:** publish a canonical-consumer inventory, instrument usage, then remove/deprecate only with separate approval.
- **Proposed phase:** F4.7 — Premium Runtime Ownership Cleanup.

## Regressions

**None found.** In particular, the canonical lifecycle, new Weekly Feedback field collection, response correlation (`current.id` plus `{message, respondedAt}`), pending resolution, retry/idempotency and Projeto LM isolation remain represented by current code/tests. Historical `waist` compatibility is not a regression because the current UI collection contract does not emit it. Staging visual/integration unknowns are not labeled regressions.

## Technical Debt

- Legacy and canonical nutrition endpoints/presenters have divergent public field sets.
- `publicNutritionPlan` includes `student_email` and internal plan `id` in a student-self DTO even though the renderer does not need them. This is not cross-student exposure, but DTO minimization should accompany canonicalization.
- Progression and weekly plans use legacy email association in active handlers even though backfill support adds canonical `student_id`.
- Alert/confirm messaging remains in several professional mutations; operations are protected against immediate double-clicks but feedback is inconsistently accessible.
- The Student Record composition does not include activity timeline events as a named collection; follow-ups, feedbacks and pending are separate fragments rather than a unified 360º history.
- Root/public/assets byte copies are gate-protected deployment debt.
- The newer nutrition student page is UI-orphaned from Home/navigation while still covered by tests/PWA inventory.
- No evidence of obviously heavy client work was found; baseline gates, not speculative optimization, remain the performance criterion.

## Recommended F4 Roadmap

1. **F4.1 — Progression Contract and Professional Loop**: first prevent data loss, then expose student-scoped professional history/feedback and parity tests.

## Final Verdict

Consultoria Premium is **operationally credible but not operationally complete**. Lifecycle and Weekly Feedback should remain closed/validated. Registration, anamnesis, Workspace core and nutrition version storage are also supported by strong evidence. Completion is blocked at S1—not S0—by three product chains: lossless/visible progression, exact published-nutrition parity in the real student journey, and explicit weekly-plan/training operational ownership.

No production file was altered by F4.0. The next work should implement the evidence-ranked blocks above, not reopen validated lifecycle or Weekly Feedback contracts and not merge Premium lifecycle/data with Projeto LM.
