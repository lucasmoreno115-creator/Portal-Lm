# F6.0 — Student UX Audit

## Executive Result

**UX_GAPS_FOUND.** The finite V1 backlog contains **4 findings: UX0 0, UX1 4, UX2 0, UX3 0**. All four are `REQUIRED_FOR_V1`; there are no `ACCEPTED_NON_BLOCKER` items. This is an audit-only result: no finding is fixed by this change.

The student can authenticate, is routed according to the existing Premium lifecycle, can submit the anamnesis and weekly check-in, can find the Home CTAs, and can read intentional empty/error states on Nutrition and Weekly Feedback. Four concrete gaps remain: Nutrition is a dead end; Progression can be saved repeatedly without a perceptible success state; Progression history has no controlled loading/error UI; and Home intentionally hides the whole document while access is checked.

This report freezes the F6.0 backlog. It does not invite a second open-ended UX audit and does not assess desirable V2 features.

## Method

1. Inspected the canonical student HTML, shared navigation/access code, and student-side Nutrition and Weekly Feedback renderers.
2. Reused the repository's deterministic Node test and QA infrastructure. Added `qa:lm:student-ux-audit` to inventory canonical surfaces, resolve every local Home CTA, verify lifecycle copy, viewport declarations, the approved Weekly Feedback fields, back navigation, and existing mutation guards.
3. Cross-checked lifecycle transitions with the existing lifecycle, deactivation, and reactivation suites; no lifecycle contract was invented or changed.
4. Assessed the requested `390 × 844` mobile and `1440 × 900` desktop layouts from their responsive CSS/DOM contracts and the repository's existing Chromium/CDP viewport infrastructure. No visual screenshot is attached because the reproducible findings are DOM/state defects rather than ambiguous visual observations; no runtime code was changed.
5. Exercised controlled success/error/empty behavior through existing UI tests and source-level deterministic checks. External destinations were inventoried but not deeply tested over the internet.
6. Ran the mandatory F4, F5, database, baseline, Project LM, Premium QA, and full test gates at the audit head. Results are recorded below.

Limit: this local audit did not impersonate a production student or modify remote data. Runtime-state conclusions use deterministic repository fixtures and contracts. Console/network conclusions therefore cover controlled harness execution rather than live production telemetry.

## Findings

### UX1

#### UX-PREM-001 — Nutrition is a dead end

- **Severity:** UX1 — HIGH
- **Page/route:** `portal-premium-nutrition-plan.html`
- **Viewport:** `390 × 844` and `1440 × 900`
- **Student state:** `ACTIVE`
- **Precondition:** Authenticated Premium student follows “Plano Alimentar” from Home.
- **Steps:** (1) Open Home. (2) Activate “Plano Alimentar”. (3) Inspect the page after loading, empty, or error rendering. (4) Attempt to return through product navigation.
- **Expected:** A reasonable Home/back/shared-navigation affordance exists.
- **Actual:** The canonical Nutrition document contains only its content and print/PDF action; it renders no Home link, logo link, back control, or shared menu. Browser history is the only escape.
- **Impact:** A principal student function ends the in-product journey, matching the audit definition of a dead end. This is especially confusing in standalone/PWA entry where browser chrome may be absent.
- **Recommended fix:** Add the existing Premium Home/shared-navigation affordance without redesigning the page or changing the API.
- **Regression evidence required:** At both viewports, enter from Home, activate the in-page return affordance, and assert arrival at Premium Home for plan, empty, and controlled-error states.

#### UX-PREM-002 — Progression save can duplicate and has no perceptible success confirmation

- **Severity:** UX1 — HIGH
- **Page/route:** `portal-progressao.html`
- **Viewport:** `390 × 844` and `1440 × 900`
- **Student state:** `ACTIVE`
- **Precondition:** A valid calculated recommendation is visible and “Salvar progressão” is enabled.
- **Steps:** (1) Fill exercise, target range, load, repetitions, and execution quality. (2) Select “Calcular”. (3) Rapidly activate “Salvar progressão” twice on a delayed connection. (4) Observe the button and completion state.
- **Expected:** While saving, repeat activation is blocked; completion produces a clear success confirmation.
- **Actual:** The save handler has no in-flight guard/disabled state and issues one POST per activation. On success it only reloads history; it does not announce or display that the progression was saved.
- **Impact:** Students can create duplicate records and may repeat the operation because receipt is ambiguous.
- **Recommended fix:** Disable/label the save CTA while pending and expose an `aria-live` or visible success/error state; do not change persistence contracts.
- **Regression evidence required:** A delayed double activation yields exactly one POST, the CTA is pending/disabled, success is perceptible, and failure restores a usable CTA.

#### UX-PREM-003 — Progression history has no loading or controlled error state

- **Severity:** UX1 — HIGH
- **Page/route:** `portal-progressao.html`
- **Viewport:** `390 × 844` and `1440 × 900`
- **Student state:** `ACTIVE`
- **Precondition:** Authenticated student; delay or reject `GET /api/portal/progression`.
- **Steps:** (1) Open Progression with a delayed response and inspect Histórico. (2) Repeat with a controlled failed response. (3) Inspect console and page state.
- **Expected:** The section indicates loading; a failure leaves a comprehensible, intentional error state and no uncaught rejection.
- **Actual:** Histórico starts empty. `loadHist()` has neither initial loading copy nor `try/catch`; rejection leaves the section blank and creates an unhandled promise rejection.
- **Impact:** A critical surface appears unfinished or frozen, and the student cannot distinguish “no history” from request failure.
- **Recommended fix:** Render simple loading and controlled error copy around the existing request; retain the current “Sem histórico” empty state.
- **Regression evidence required:** Delayed, zero-record, populated, and rejected fixtures respectively show loading, intentional empty, records, and friendly error with no unhandled rejection.

#### UX-PREM-004 — Home access loading is a blank document

- **Severity:** UX1 — HIGH
- **Page/route:** `portal-premium-home.html`
- **Viewport:** `390 × 844` and `1440 × 900`
- **Student state:** `ACTIVE` (also observable during stale `ENDED` → onboarding routing)
- **Precondition:** Authenticated Premium session; delay `GET /api/portal/premium/access-state`.
- **Steps:** (1) Navigate to Premium Home. (2) Hold the access-state response. (3) Observe before the response resolves.
- **Expected:** Minimal visible feedback makes clear that access/Home is loading.
- **Actual:** Inline CSS sets the entire `body` to `visibility:hidden`; it is revealed only after successful access resolution. The viewport is completely blank during the request.
- **Impact:** On a slow mobile connection the primary hub looks broken or frozen, despite an active request.
- **Recommended fix:** Keep a minimal visible access-loading status while preserving lifecycle redirects and F5 access boundaries.
- **Regression evidence required:** With a delayed access response, visible Portuguese loading feedback exists; ACTIVE still reveals Home, ENDED still routes away, and failures do not expose protected content.

## Navigation / Dead Ends

Shared navigation exposes Home, Check-in, Nutrition, Progression, support, and logout for Premium. Weekly Feedback explicitly returns to Home and did not regress its historical dead end. Progression receives the shared menu. Nutrition does not, producing the only confirmed dead end (UX-PREM-001). Home local CTA destinations exist and no principal CTA enters Projeto LM.

## Accessibility Sanity

- Primary controls have visible text; the Weekly Feedback iconography is supplementary.
- Login and Progression controls are enclosed by understandable labels. Weekly Feedback creates associated wrapping labels for every approved field.
- Status areas on Nutrition/Weekly Feedback and Anamnese's sending state provide understandable text; Weekly Feedback uses live status regions.
- Functional logo fallback has an accessible LM label and the logo image has alternative text.
- No CSS rule explicitly removes keyboard focus across the audited pages.
- Heading structure remains understandable on the main surfaces.
- UX-PREM-002's missing announced success and UX-PREM-004's invisible loading state are included in the required backlog rather than duplicated as accessibility findings.

This is a limited sanity check, not a WCAG AA conformance statement.

## Console / Network

- Controlled canonical requests for access state, Nutrition, Weekly Feedback current/history, Anamnese, and Progression match current endpoints; no unexpected legacy endpoint was found.
- Local Home destinations resolve to repository files. MFIT and WhatsApp are classified `EXTERNAL` and were not deeply exercised.
- No product-caused `TypeError` or `ReferenceError` was observed in deterministic scoped tests.
- A rejected initial Progression history request is not caught and therefore produces an unhandled rejection (UX-PREM-003).
- No critical request loop was found.

## Positive UX Evidence

- Login invalid/error copy is comprehensible and valid Premium/Projeto LM entry remains separated.
- Lifecycle routing covers pre-anamnesis, review, ready, active, ended, and reactivated access without exposing protected Premium modules early.
- Anamnese has step navigation, guards repeat submission, exposes a pending label, preserves draft answers on error, and lands on explicit review confirmation.
- Nutrition has intentional loading, unpublished-plan, and friendly failure copy; long content uses text nodes rather than raw markup.
- Progression labels exercise, target zone, load, repetitions, execution quality, and recommendation clearly; its zero-record state and legacy fallbacks avoid `undefined`/`NaN`.
- Weekly Feedback back navigation, loading, retry, zero-history, pending-response, success, and professional-response states are explicit. Waist and abdomen are absent from the approved questionnaire.
- Professional response includes a visible heading, message, and localized response date and remains readable in current/history views.
- No cross-student fixture identity or wrong-product CTA was found on Premium pages.
