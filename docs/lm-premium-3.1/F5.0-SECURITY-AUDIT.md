# F5.0 — Security Audit

## Executive Result

**NO_BLOCKING_SECURITY_GAPS_FOUND**

This repository/application audit found **0 S0, 0 S1, 2 S2, and 0 S3** vulnerabilities. The two confirmed findings are stored self-XSS in authenticated legacy student pages. Neither crosses student ownership or reaches the canonical Premium UI, so both are finite, accepted V1 non-blockers. This result does not claim that the system is absolutely secure.

## Source SHA

Audit baseline: `aa5f2e0e7466d6a18c710de9fe1514b4da08ef99` (current `main` supplied for F5.0, before audit-only files).

## Method

* Static inspection of `workers/api.js`, authentication services, Premium application/repositories/presenters, browser render sinks, SQL construction, configuration, and tracked files likely to contain credentials.
* Route inventory from the Worker dispatch tree; no production requests or external scanning.
* Deterministic Node 22 tests through the real Worker `fetch` handler and an isolated temporary `SqliteD1` database.
* Two ACTIVE Premium identities (Student A and Student B), deliberate ID/email/field tampering, missing/invalid/student/admin authentication, published/draft nutrition versions, lifecycle evidence, public DTO inspection, and benign non-executable XSS markers.
* Existing E2E evidence was reused for full lifecycle transition/replay and shared-identity Project LM preservation. The dedicated command is `npm run qa:lm:security-audit`.

## Attack Surface

The existing surface comprises public health/login/bootstrap endpoints; authenticated shared-identity Portal and Project LM APIs; Premium student reads/mutations; and the administrative Workspace, Student Record, nutrition, anamnesis, feedback, pending-item, lifecycle, operational, and legacy administration APIs. Static HTML is public delivery, not a protected-data boundary.

### S2

#### SEC-PREM-001 — Stored self-XSS sink in legacy weekly check-in history

* **Severity:** S2 — MEDIUM.
* **Affected surface:** authenticated legacy student check-in page.
* **Affected routes:** `POST /api/portal/checkin`, `GET /api/portal/checkins`; sink in `public/portal-checkin.html` (and its root delivery copy).
* **Precondition:** an authenticated Premium student submits markup in a textual check-in field, then opens the legacy check-in history page. Ownership prevents another student from selecting it.
* **Reproduction:** submit a harmless marker such as `<svg data-security-test="xss">` in `main_difficulty`; read the same student's history; observe that the page template concatenates the returned value into `hist.innerHTML`. Do not add executable attributes.
* **Expected:** user-controlled text is inserted as a text node or HTML-escaped.
* **Actual:** the persisted marker reaches an HTML parser sink and becomes markup.
* **Impact:** script-capable markup could execute in the submitting student's authenticated legacy page and access that student's browser-held Portal credentials/data. No cross-student or admin execution was demonstrated; the canonical weekly feedback page uses `textContent` and is not affected.
* **Root cause:** direct template interpolation into `innerHTML` without contextual escaping.
* **Recommended fix:** render history with DOM nodes and `textContent`, or apply the established HTML escape helper to every dynamic value before insertion.
* **Regression test required:** persist a benign marker through real HTTP and assert that the browser DOM contains text, not an SVG element, on the legacy page.

#### SEC-PREM-002 — Stored self-XSS sink in progression history

* **Severity:** S2 — MEDIUM.
* **Affected surface:** authenticated Premium progression page.
* **Affected routes:** `POST /api/portal/progression`, `GET /api/portal/progression`; sink in `public/portal-progressao.html` (and its root delivery copy).
* **Precondition:** an authenticated Premium student supplies markup in the unrestricted `exercise` or `recommendation` text and opens their progression history.
* **Reproduction:** `npm run qa:lm:security-audit` stores the harmless marker `<svg data-security-test="xss">` as Student A through real Worker HTTP, reads it back, and statically confirms the value is interpolated into `hist.innerHTML`.
* **Expected:** persisted student text is rendered as text.
* **Actual:** the exact marker reaches the unsafe HTML sink and would be interpreted as markup by a browser.
* **Impact:** same-account stored XSS can expose the submitting student's browser-held credentials/data. Server-derived ownership prevents selecting B or affecting B, and no professional/admin sink was demonstrated.
* **Root cause:** persistence correctly accepts text, but the legacy browser renderer does not encode it for an HTML context.
* **Recommended fix:** replace the history template with created elements using `textContent` (preferred), or escape all interpolated data.
* **Regression test required:** local browser/DOM test proving the marker remains text and no `[data-security-test=xss]` element exists.

## Positive Security Evidence

* Every `/api/admin/*` route except the intentionally public session login/logout and non-sensitive cutover bootstrap passes through one server-side authorization boundary; hiding frontend buttons is not relied upon.
* Premium reads derive the canonical student from validated email/token headers. Nutrition current accepts no resource selector and progression ignores attempted B ownership, timestamp, and ID fields.
* Nutrition `current` returns the published active A plan, never A's draft or B's plan, and uses an explicit public presenter.
* The public professional response presenter exposes only `message` and `respondedAt`; canonical UI rendering uses `textContent`.
* Anamnesis rejects client-supplied identity/status fields and caps the serialized request at 100,000 bytes.
* Parameter binding is used for client-derived SQL values. Dynamic filtering uses fixed SQL fragments and bound values.
* Sensitive lifecycle mutations use POST/PATCH, reject wrong methods through route dispatch, and existing closure proves repeated deactivate/reactivate/decision actions do not duplicate state.

## Project LM Isolation

Authentication identity is shared, but product authorization is evaluated separately. Premium core routes call the Premium gate and reject non-Premium/product-confused access. Existing lifecycle closure attaches a Project LM profile to the same shared identity, snapshots it, deactivates/reactivates Premium, and verifies the Project LM row and access remain unchanged. The audit introduced no runtime, schema, migration, or data changes.

## Accepted Non-Security Debt

The following reviewed facts are not vulnerabilities under the F5.0 rules: public static HTML; absence of MFA/OAuth; a long-lived student token where token expiry/logout invalidation is not an existing contract; the public non-secret admin cutover flag; monolithic dispatch; and missing global idempotency where replays do not create inconsistent or privileged state.

## Required Fixes for V1

**REQUIRED_FOR_V1: none.** There are no confirmed S0/S1 findings and neither S2 crosses an identity, role, product, or administrative boundary. F5 is therefore not blocked by this audit result.
